# HW4. IR, CFG, оптимизации, живость и раскраска

Python 3.10+, только стандартная библиотека. Это **дополнение к вашему HW3**, не новый фронтенд.

## 1. Установка в ваш репозиторий

Распакуйте архив в корень `TVDSL`: он добавляет `homeworks/HW04`, не заменяя `homeworks/HW03`.

```text
TVDSL/
└── homeworks/
    ├── HW03/                # ваше существующее решение
    │   └── main.py
    └── HW04/                # этот каталог
        ├── main.py
        ├── ir.py
        └── ...
```

Решение согласовано с HW3 ветки `HW01`, коммит `df309682de33a5cfe9a2d5b716e6968ac1be62b4`. Ваш HW3 запускается отдельным процессом через его существующий интерфейс `main.py source --semantic --json`. Имена модулей `main`, `parser` и `semantic` поэтому не конфликтуют. Фронтенд и его AST не переписаны.

## 2. Быстрый запуск из homeworks/HW04

```bash
# Полный путь: исходник -> ВАШ HW3 -> аннотированный AST -> HW4
python3 main.py examples/constants.funny --opt const,algebraic,dce,cse --out generated/demo --run f --args '[5]'

# Все оптимизации выключены по умолчанию
python3 main.py examples/constants.funny --out generated/no_opt

# Другое местоположение HW3
python3 main.py examples/loop_sum.funny --hw3-dir ../HW03 --opt const,algebraic,dce --run f --args '[10]'

# Проверка нескольких входов с эталонными результатами
python3 main.py examples/constants.funny --opt const,algebraic,dce --verify examples/constants.inputs.json

# Ограничение для ОЦЕНКИ spill-кандидатов
python3 main.py examples/constants.funny --opt const,algebraic,dce --registers 1
```

`--run` выполняет исходный и оптимизированный IR на одинаковых входах и сравнивает результат либо тип и сообщение исключения. `--verify` дополнительно проверяет явно заданное поле `expected`, если оно есть. Коды завершения: 0 — успех/совпадение наблюдений; 1 — ошибка компиляции, ввода/вывода или несоответствие результатов; ошибки аргументов argparse дают 2.

Если HW3 нашёл ошибки, IR не создаётся. Для JSON с `ok=false`, диагностикой, отсутствующим типом выражения или `<error>` генерация также запрещена. Произвольный внешне подделанный JSON не является доверенным результатом полноценной проверки HW3: отсутствие этих признаков не доказывает корректность всей программы.

## 3. Работа без установленного HW3

Можно передать уже аннотированный AST. Поддержаны оболочка HW3 с полем `ast` и непосредственно дерево с `node: Program`.

```bash
python3 main.py tests/hw3_pos_types_ok.json --ast --opt const,algebraic,dce --run f --args '[3]'
python3 main.py examples/constants.ast.json --ast --opt const,algebraic,dce,cse --out generated/demo --run f --args '[5]'
python3 main.py examples/loop_sum.ast.json --ast --opt const,algebraic,dce --run f --args '[10]'
```

`tests/hw3_pos_types_ok.json` — прочитанный из вашего репозитория эталон HW3. `examples/*.ast.json` — **явно сконструированные типизированные тестовые деревья**, а не заявленные результаты нового запуска HW3. Для них приложены соответствующие `.funny` и ожидаемые результаты.

## 4. Проверки

```bash
# Независимые тесты HW4 и тест на реальном формате эталонного AST HW3
python3 run_tests.py

# Обязательный для вашего репозитория сквозной прогон через установленный HW3
python3 run_tests.py --hw3-dir ../HW03

# Только unit-тесты
python3 -m unittest test_ir -v
```

В выполненном здесь прогоне: 36 unit-тестов, 35 типизированных программ, 72 входа/наблюдения на каждую из 16 комбинаций флагов — 1152 дифференциальные проверки. Дополнительно 700 проверок на целочисленных входах, с фиксированным seed для воспроизводимости.

Проверяются ветвления, циклы, вызовы, рекурсия, взаимная рекурсия, short circuit, затенение имён, функциональные массивы, ошибки времени выполнения, DCE через границы блоков, инвалидация CSE, живость, правильность цветов, JSON round-trip и CLI. Для тестовых программ проверяются не только равенство до/после, но и вручную заданные результаты/типы исключений.

Полный сквозной запуск исходников через настоящий HW3 в текущей среде **не выполнялся**: использованы прочитанные интерфейсы и эталон JSON из GitHub, а не локально клонированный фронтенд. `run_tests.py --hw3-dir ../HW03` делает этот отдельный прогон на всех 35 `.funny` и проверяет отказ при ошибке HW3. Его статус явно отражается в `generated/test_results.json`; без флага он равен `not_run`, а не ложному `passed`.

## 6. Формат IR

Подробный JSON-контракт и Python API описаны в `IR_API.md`.

IR — плоский трёхадресный код с явными переходами и результатами. Вызов допускает произвольное число аргументов — это обычное расширение TAC для call. `types` хранит строковые типы локальных значений и временных из HW3. Переменные переименовываются в `v1_x`, `v2_r`, ... с учётом областей; временные — `t1`, `t2`, ... в каждой функции, метки `L1`, ... уникальны во всей компилируемой программе. Одинаковые имена локальных разных функций допустимы: у каждого вызова собственный frame.

Одна арифметическая операция/сравнение

`t = not b`

У `load`, как и у других вычислений, явно указан результат; тип берётся из таблицы `types`. Именованный результат `returns r: T` из HW3 переводится в `return r` в конце функции. Синтаксис с отдельными ранними `return` и `let` не добавляется: ваш HW3 использует `var` и именованный результат.

## 7. Семантика конструкций

-   Арифметика и сравнения — типизированные операции над допустимыми операндами HW3.
-   `and`/`or` имеют настоящее короткое замыкание через переходы: невыбранный правый операнд не вычисляется.
-   Вызовы поддерживают локальные функциональные псевдонимы `var h = f; r = h(x);`.
-   Массивы — значения: `a[i]=v` создаёт новый массив через `store`, не меняя прежние копии. Вложенное обновление использует вложенные `store`. RHS вычисляется перед адресной частью присваивания; индексы адресной части — слева направо. Выражения не имеют присваиваний и функции не меняют переменные чужого frame.
-   Индексы только от 0 до `length-1`; отрицательные индексы, в отличие от Python, запрещены.
-   `requires` превращается в `assume`, `ensures` — в `assert` перед `return`; `invariant` проверяется при каждом входе в заголовок цикла, в том числе перед последним ложным условием.
-   `assume false` в проверочном интерпретаторе даёт `AssumptionFailed`; это не попытка продолжить выполнение на недопустимом пути.
-   Интерпретатор проверяет число/типы входных аргументов, ограничивает шаги и глубину рекурсии. Лимиты нужны для тестового runner, не являются семантическим доказательством завершимости.

Целые пока математические, без переполнения. Деление — целочисленное с усечением к нулю, без преобразования в float. При будущем JVM-кодогене потребуется явно выбрать представление целых (например, BigInteger для этой семантики) либо согласованно изменить VM/свёртку на 32-битную арифметику. Генерации байткода в HW4 нет.

## 8. CFG и живость

Блоки выделяются по лидерам: вход, цели переходов и инструкции после терминаторов; метки также начинают блок. CFG учитывает явные переходы, оба исхода branch и fall-through. Return не имеет преемников. Достижимость маркируется, но недостижимые блоки автоматически не удаляются.

Живость решается до неподвижной точки:

```text
OUT[B] = union(IN[S] for S in successors[B])
IN[B]  = USE[B] union (OUT[B] - DEF[B])
```

Затем строится живость перед/после каждой инструкции обратным проходом. Это важно для циклов и для значения, вычисленного в одном блоке и прочитанного в другом.

## 9. Оптимизации

По умолчанию все выключены. Флаги независимы: `--opt const`, `--opt algebraic`, `--opt dce`, `--opt cse` или любое их сочетание.

-   `const`: локальное распространение констант, свёртка бинарных/унарных операций. При переопределении имени его прежняя константа забывается. Информация не переносится через границу блока. Деление на ноль не вычисляется при компиляции — инструкция сохраняется.
-   `algebraic`: `x+0`, `0+x`, `x-0`, `x*1`, `1*x`, `x*0`, `0*x`, `x/1`. Уже вычисленные операнды не «откатываются»: если вычисление операнда могло упасть, оно сохраняется даже после упрощения результата.
-   `dce`: обратное удаление ненужных присваиваний/безопасных вычислений с использованием живости на выходе блока. Деление, загрузки из массива, вызовы, проверки и управление не удаляются, даже если их результат не используется. Исключения — наблюдаемое поведение, поэтому агрессивное удаление было бы ошибкой.
-   `cse`: повторное одинаковое выражение в блоке заменяется копированием ранее полученного результата. Записи, меняющие операнды/результат, инвалидируют кэш; вызов консервативно очищает кэш. CSE не гарантирует уменьшение общего числа инструкций: bin может стать copy, но вычислительных операций станет меньше.

Проходы повторяются до стабильного IR. Нет SSA, глобального распространения констант, оптимизации переходов, инлайнинга или переупорядочивания эффектов.

## 10. Граф конфликтов и жадная раскраска

Узлы — все используемые локальные имена, параметры и временные функции. Из графа также выделяется отображение `temp_colors` только для временных. Рёбра соединяют одновременно живые значения; дополнительно учитываются определения и live-out. Попарные конфликты live-in важны, например, для двух одновременно нужных параметров.

Узлы сортируются по убыванию степени, затем по имени для воспроизводимости. Каждому назначается минимальный свободный цвет, начиная с 0. Это корректная жадная, но не обязательно минимальная раскраска.

`--registers K` сообщает имена с цветами `>=K` как spill-кандидаты. Реальные загрузки/выгрузки не вставляются; это анализ, не завершённый машинный allocator. Цвета пока виртуальные и нетипизированные: для JVM ещё понадобятся соглашение о параметрах, типы/ширины слотов и проверка stack map frames. Нельзя считать это уже сгенерированным корректным JVM-байткодом.

## 11. Метрики и наблюдаемый эффект

В `examples/constants.funny`:

```text
a = 2 * 3
b = a * 1
r = x + a + b
```

Реально получено: 8 -> 4 инструкции, 4 -> 2 временные, 3 -> 1 цвет. В подсчёт инструкций включён `return`, но не метки; поэтому это 8 -> 4, а не 7 -> 3 вычислительных/копирующих инструкции из слайда. В этом примере `x` после первого сложения больше не нужен, поэтому после оптимизации достаточно одного виртуального цвета. Значения на протестированных входах сохраняются: `f(x)=x+12`.

Дампы, графы и численные результаты находятся в `generated/constants/`; дополнительные примеры — `generated/loop_sum`, `generated/cse`, `generated/nested_array_store`. Больше деталей — `REPORT.md`.

## 12. Структура

-   `ir.py` — генератор, CFG, живость, оптимизации, раскраска, дампы и проверочная VM.
-   `main.py` — CLI и мост к существующему HW3.
-   `fixtures.py` — конструкторы явно заданных тестовых AST и соответствующего исходного текста.
-   `test_ir.py`, `run_tests.py` — независимые проверки и опциональная настоящая интеграция.
-   `tests/` — эталон из вашего HW3 и ожидаемые наблюдения для новых тестов.
-   `examples/` — исходники, типизированные тестовые деревья и входы.
-   `IR_API.md`, `REPORT.md`, `INTEGRATION.md` — контракт и отчётность.
