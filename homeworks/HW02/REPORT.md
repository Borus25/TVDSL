# Отчёт по HW2: синтаксический анализ Funny, ветка LL(1)

## 1. Выбор ветки

Выбрана **LL(1), рекурсивный спуск вручную**. Причины:

- грамматика Funny со слайда после двух стандартных преобразований (хвосты вместо
  левой рекурсии и вынесение общего префикса `IDENT`) становится LL(1) без конфликтов;
- каждый метод `parse_X` в `parser.py` один к одному соответствует нетерминалу `X`
  в `grammar.txt`, так что соответствие кода грамматике видно глазами;
- в рекурсивном спуске легко писать понятные сообщения (`expected ')' but got ';'`)
  и ставить точки восстановления там, где нужно;
- не нужны внешние инструменты (bison/ply), проект на чистом Python.

## 2. Грамматика

Файл `grammar.txt`: часть 1 — EBNF со слайда с пометками отклонений, часть 2 — LL(1)-форма.

Что сделано, чтобы грамматика стала LL(1):

| Проблема | Где | Преобразование |
|---|---|---|
| Повторения `( op X )*` (в BNF это левая рекурсия `A → A op X`) | `or_expr`, `and_expr`, `add_expr`, `mul_expr`, `params`, аргументы | хвосты: `A → X A_tail`, `A_tail → op X A_tail \| ε`; в коде — цикл `while` |
| Общий префикс `IDENT` | `assign` (`IDENT = …` и `IDENT [ … ] = …`), `primary` (`IDENT`, `IDENT[…]`, `IDENT(…)`) | факторизация: `stmt → IDENT assign_tail`, `primary → IDENT ident_tail` |
| Необязательные части | `requires?`, `ensures?`, `else`, `invariant`, `;` | ε-правила `requires → 'requires' expr \| ε` и т. п. |

Приоритеты и ассоциативность заданы уровнями грамматики (от слабого к сильному):
`or` < `and` < `not` (префикс) < сравнения (неассоциативны) < `+ -` < `* /` < унарный `-`.
Бинарные операторы левоассоциативны: в цикле `while` новый узел строится над уже
собранным левым (`a - b - c` → `(a - b) - c`). Сравнения неассоциативны:
`a < b < c` — ошибка с подсказкой использовать `and`.

**Метрики LL(1)-анализа** (`python3 main.py --grammar`):

| Показатель | Значение |
|---|---|
| Нетерминалов | 36 |
| Правил (альтернатив) | 74 |
| Терминалов | 37 |
| Заполненных клеток M[A, a] | 255 |
| **Конфликтов LL(1)** | **0** |

Примеры FIRST/FOLLOW (полностью — в выводе `--grammar`):

- FIRST(stmt) = { IDENT, if, while, assert, assume, `{` }
- FIRST(expr) = { INT, IDENT, true, false, length, `(`, `-`, not }
- FOLLOW(stmt) = FIRST(stmt) ∪ { `}` } — в нём **нет `;`**, поэтому `semi → ';' | ε` без конфликта;
- FOLLOW(ident_tail) не содержит `(` и `[` — поэтому `r = x` без `;` и следующий оператор не спутаются;
- FOLLOW(requires) = { ensures, `{` }, FOLLOW(params) = { `)` }.

## 4. AST

Узлы — список со слайда: `Program, Function, Block, Assign, If, While, Assert, Assume,
ArrayIndex, BinaryOp, UnaryOp, Call, Ident, Int, Bool`. Все узлы хранят `pos`.
Вывод: JSON (по умолчанию, для snapshot-тестов) и S-выражения (`--sexp`).
`from_dict` восстанавливает узлы из JSON — следующие этапы могут читать AST из файла.

Обновление массива `a[i] = v` в AST хранится как в грамматике: `Assign(target=ArrayIndex(a, i), value=v)`.
Флаг `--desugar` (функция `desugar`) превращает его в функциональное копирование
`a = store(a, i, v)`: создаётся новый массив, отличающийся одной ячейкой.

## 5. Обработка ошибок (режим паники)

Каждая ошибка печатается с позицией токена: `error: <что> at строка:столбец (пояснение)`.

**Как работает.** При ошибке пишется диагностика и бросается исключение `SyntaxErr`.
Его ловит ближайшая точка восстановления и пропускает токены до якоря:

| Точка восстановления | Якоря (синхронизирующее множество) | Что потом |
|---|---|---|
| оператор (`parse_block`) | FOLLOW(stmt) ∪ { `;`, `}` } без IDENT, плюс `function`, EOF | `;` съедается, разбор следующего оператора |
| условие `( … )` у if/while | `)`, `{`, `;`, `}`, `function`, EOF | `)` съедается, разбирается тело и `else` |
| заголовок функции | `{`, `function`, EOF | тело всё равно разбирается — в нём ищутся свои ошибки |
| верхний уровень | `function`, EOF | следующая функция |

IDENT из якорей оператора исключён сознательно: идентификаторы стоят внутри
сломанного выражения, и остановка на них давала лавину ложных ошибок.
Вторая ошибка в той же позиции, что и предыдущая, не печатается (это каскад).

**Почему не зацикливается.** Цикл блока продолжается, только пока не встретились `}`,
`function` или EOF. После каждого восстановления проверяется, съеден ли хоть один
токен с начала оператора; если нет — один токен выбрасывается принудительно. Так что
каждая итерация продвигает вход минимум на токен. Проверено тестами: 1000 случайных
строк из мусора и 3000 испорченных программ, ни одна не зависла; `main.py --test`
дополнительно ограничивает каждый тест 5 секундами.

**Позиции после ошибки обновляются**: в `neg_12_many_errors` 8 ошибок на 8 разных
строках, в `neg_16` — ошибка в заголовке и отдельная ошибка в теле той же функции.

## 7. Отклонения от грамматики слайда

| # | Отклонение | Причина |
|---|---|---|
| Δ1 | `program := function+` вместо `function*`: пустой ввод — ошибка | на слайде «Тесты» пустой ввод в списке негативных |
| Δ2 | `;` после присваивания, `assert`, `assume` разрешена, но не обязательна | грамматика слайда `;` не содержит, а все тесты слайда и демо bison её пишут. Необязательная `;` поддерживает оба варианта и не ломает LL(1): `;` нет в FOLLOW(stmt). Если после оператора стоит не `;`, не `}` и не начало оператора — ошибка `expected ';'` |
| Δ3 | `while (…) invariant expr { … }` — инвариант необязателен | токен `INVARIANT` есть в лексере HW1; без него цикл верифицировать нельзя |
| Δ4 | вызовы `f(x, y)` и `length(a)` в `primary` | узел `Call(name, args)` есть в списке AST на слайде, а токен `LENGTH` — в лексере HW1 |
| — | `uses` распознаётся лексером (HW1), но в грамматике его нет: `uses` — синтаксическая ошибка | на слайде конструкции с `uses` нет |
| — | модуль AST называется `funny_ast.py`, а не `ast.py` | `ast.py` перекрывает стандартный модуль и роняет программу на Python 3.9–3.12 (проверено), см. README |
| — | комментарий в лексере тянется до конца строки даже с не-ASCII | в HW1 русская буква обрывала комментарий, и его хвост лексировался как код |

## 8. Выводы

- Грамматика Funny после устранения левой рекурсии и факторизации — LL(1) без конфликтов,
  и это проверяется автоматически по `grammar.txt`.
- Рекурсивный спуск совпадает с табличным LL(1)-разбором на тысячах входов, то есть
  парсер реализует именно ту грамматику, что записана в `grammar.txt`.
- Режим паники с якорями из FOLLOW и принудительным продвижением находит несколько
  ошибок за проход и не зацикливается.
- Слабое место паники — после ошибки пропускается остаток оператора, и ошибки внутри
  него не находятся до следующей `;`. Это плата за отсутствие каскадов.

## 9. Ответы на вопросы для защиты

**Чем LL(1) отличается от LR(SLR)? Когда что выбирать?**
LL(1) строит дерево сверху вниз: глядя на один следующий токен, сразу выбирает правило
(предсказание). LR строит снизу вверх: сдвигает токены в стек и сворачивает правую часть
правила, когда она целиком собрана. LR принимает больше грамматик (левая рекурсия разрешена,
решение откладывается до конца правила), но таблицы генерируются инструментом (bison),
а конфликты shift/reduce надо понимать. LL(1) проще написать вручную, сообщения об ошибках
понятнее, но грамматику надо приводить к LL(1). Для небольшого языка с ручным парсером и
хорошими сообщениями — LL(1); для большой «естественной» грамматики с генератором — LR.

**Как проверить, что грамматика LL(1)? Что делать, если нет?**
Для каждой пары альтернатив `A → α | β`: FIRST(α) ∩ FIRST(β) = ∅, а если одна из них
выводит ε, то FIRST другой ∩ FOLLOW(A) = ∅. Эквивалентно: в таблице M[A, a] нет клеток
с двумя правилами. Это делает `ll1.py` (`main.py --grammar`). Если не LL(1): убрать левую
рекурсию (`A → A a | b` → `A → b A'`, `A' → a A' | ε`), факторизовать общие префиксы
(`A → x y | x z` → `A → x A'`, `A' → y | z`), а если остался конфликт — переписать правило
или решить его в коде (как классический dangling else: прицепить `else` к ближайшему `if`).

**Что такое FIRST и FOLLOW? Пример.**
FIRST(α) — терминалы, с которых может начинаться строка, выводимая из α (и ε, если α выводит
пустую). FOLLOW(A) — терминалы, которые могут стоять сразу после A в какой-либо сентенциальной
форме. Пример из нашей грамматики: FIRST(stmt) = {IDENT, if, while, assert, assume, `{`};
FOLLOW(params) = {`)`}, поэтому `params → ε` выбирается, когда следующий токен `)`.
FOLLOW(ensures) = {`{`}: если после `returns r` идёт `{`, то и `requires`, и `ensures` пусты.

**Как работает режим паники? Почему не зацикливается?**
При ошибке парсер сообщает о ней и пропускает токены до якоря — токена из FOLLOW
восстанавливаемого нетерминала (или `;`, `}`), затем продолжает так, будто этот нетерминал
разобран. Не зацикливается, потому что каждая итерация цикла разбора съедает хотя бы один
токен: якорь `;` съедается, якоря-начала операторов разбираются следующей итерацией, `}`/EOF
завершают цикл, а на крайний случай токен выбрасывается принудительно (см. раздел 5).

**Как в bison разрешаются shift/reduce конфликты?**
По умолчанию bison выбирает shift (и предупреждает). Явно — приоритетами: у правила приоритет
его последнего терминала (или заданный `%prec`), у токена — из `%left/%right/%nonassoc`
(чем ниже строка объявления, тем выше приоритет). Если приоритет токена выше — shift, ниже —
reduce, равны — по ассоциативности: `%left` → reduce, `%right` → shift, `%nonassoc` → ошибка.
Reduce/reduce решается в пользу правила, записанного раньше, — это почти всегда ошибка грамматики.

**Как связаны AST и грамматика?**
AST — это дерево разбора без синтаксического шума: скобки, `;`, ключевые слова и
вспомогательные нетерминалы (`*_tail`, `semi`, `ident_tail`) в него не попадают, а цепочки
хвостов сворачиваются в бинарные узлы с нужной ассоциативностью. Каждому «содержательному»
правилу грамматики соответствует узел: `if` → `If`, `assign` → `Assign`, `IDENT [ expr ]` →
`ArrayIndex`. Тест сравнения с табличным разбором и snapshot-тесты следят, чтобы узлы
строились ровно по правилам.

**Как добавить новую конструкцию (например, for)?**
1. Лексер: строка `FOR = for` в `funny.lex` выше `IDENT`, `python3 dfa_build.py`.
2. Грамматика: в `grammar.txt` добавить альтернативу `stmt ::= … | for_stmt` и правило,
   например `for_stmt ::= 'for' '(' IDENT '=' expr ';' expr ';' IDENT '=' expr ')' block`.
3. `python3 main.py --grammar` — убедиться, что конфликтов нет (`for` не пересекается с FIRST
   других операторов).
4. AST: узел `For(var, init, cond, step_var, step, body)` в `funny_ast.py` (+ `to_sexp`);
   или сразу десахаризовать в `Block([Assign, While(cond, Block(body + [Assign]))])`.
5. Парсер: ветка `if tok.kind == "FOR": return self.parse_for()` в `parse_stmt`, добавить
   `FOR` в `STMT_START` и якоря; метод `parse_for` по правилу.
6. Тесты: `pos_*/neg_*.funny`, `main.py --test --update`, проверить эталоны глазами.
