# HW5. Темпоральные спецификации и проверка моделей

Python 3.10+ для скриптов. Основной внешний инструмент — **NuSMV / nuXmv**; A/B со Spin не заявляется.

## Важный статус сдачи

**Модели и скрипты подготовлены, Python-проверки реально выполнены. В этой среде NuSMV/nuXmv отсутствует: его проверки НЕ запускались.** В `generated/nusmv/results.json` это явно записано как `status: not_run`. Для завершения обязательного инструментального этапа нужен установленный NuSMV/nuXmv и команда из следующего раздела. Python-логи не выдаются за NuSMV-логи.

## Быстрый старт

Скопируйте каталог архива `homeworks/HW05` в свой репозиторий рядом с HW04. Исходный HW04 менять не требуется.

```bash
cd homeworks/HW05

# Построить SMV-модели, точные Python-результаты, доказательства и DOT
python3 main.py build

# Локальные тесты, без внешних зависимостей
python3 run_tests.py

# ОБЯЗАТЕЛЬНЫЙ внешний прогон, если NuSMV уже есть в PATH
python3 run_nusmv.py

# Или указать путь к установленному инструменту
python3 run_nusmv.py --binary /path/to/NuSMV
python3 run_nusmv.py --binary /path/to/nuXmv
```

Альтернативные формы CLI: `python3 main.py test`, `python3 main.py nusmv --binary /path/to/NuSMV`.

Установка NuSMV/nuXmv платформозависима; готовый исполняемый файл нужно получить с официального сайта инструмента и передать через `--binary` либо добавить в PATH. Скрипт не скачивает и не устанавливает программы автоматически. NuSMV запускается как обычный subprocess, не как Python-библиотека.

`run_nusmv.py` выполняет 30 отдельных проверок: пять вариантов модели × шесть свойств. Для каждого сохраняются `.smv`, stdout, stderr, команда, код возврата, фактическое wall time и verdict. Проверка полная символическая, без ограниченного BMC; используется `-ctt` для проверки тотальности переходов. Результат сверяется с ожидаемой таблицей, а не с правилом «все формулы обязаны быть true».

Коды возврата: 0 — ожидаемые verdict совпали; 1 — ошибка запуска/проверки/расхождение; 2 — внешний инструмент не найден. `--allow-missing` разрешает код 0 при отсутствии инструмента, но **не меняет статус not_run на passed**. Для реальной сдачи нужен `status: passed` после настоящего запуска.

## Прямой запуск без скрипта


## Модель из P09

Основная модель — ровно «запрос–ответ» из `practices/P09_temporal_specs.md`. Параметры: четыре состояния, одно начальное, атомы idle/req/ack/error, один дискретный переход за шаг. Очередей, потоков, числовых часов и нескольких одновременных заявок нет. Свойства относятся именно к этому конечному протоколу.

| Состояние | Истинные атомы | Следующие состояния original |
|---|---|---|
| s0 | idle | s1 |
| s1 | req | s1, s2 |
| s2 | ack | s0 |
| s3 | error | s3 |

Начальное состояние — s0. Недетерминизм означает, что в s1 можно ожидать сколько угодно, включая бесконечность. **Fairness не предполагается.** Из s0 достигаются только s0, s1, s2; s3 оставлено в модели специально, чтобы различать существование состояния и его достижимость.

Все состояния имеют преемников. Мы не вводим `INVAR !error` и не вырезаем ошибочные пути до проверки — это могло бы скрыть баг и сделать safety истинной искусственно.

## Варианты одной модели

- `original` — исходный граф P09 с возможным бесконечным ожиданием.
- `fixed` — удалён только переход s1→s1; запрос обязан перейти к ack.
- `error_transition` — к original добавлен переход s1→s3: ошибка становится достижимой.
- `overlap_labels` — у предыдущего варианта s3 дополнительно размечено req и ack: негатив для проверки одновременности и next-свойства.
- `bad_ack_successor` — у fixed добавлен переход s2→s1: после ack возможно не idle.

Исправление — явное изменение отношения переходов, а не доказательство, что любая реальная система обслужит запрос. Оно запрещает неограниченное ожидание на уровне выбранной модели. Мы не подменяем исправление скрытым добавлением fairness.

## Шесть свойств

| ID | Вид | Формула | Смысл |
|---|---|---|---|
| p01_no_error | safety, CTL | `AG (!error)` | Ошибка недостижима на всех путях |
| p02_no_overlap | safety, LTL | `G (!(req & ack))` | Запрос и ack не активны одновременно |
| p03_ack_to_idle | safety, LTL | `G (ack -> X idle)` | Следом за ack идёт idle |
| p04_response | liveness, LTL | `G (req -> F ack)` | Каждый запрос получает ответ |
| p05_recurring_ack | liveness, LTL | `G F ack` | Подтверждения встречаются бесконечно часто |
| p06_error_reachable | экзистенциальный запрос, CTL | `EF error` | Есть ли хотя бы один путь к ошибке? |

Итого: три safety, два liveness, два CTL среди шести формул. Первая safety записана через CTL AG, две следующие через LTL G. Для всех LTL-свойств подразумевается проверка всех путей из начального состояния.

В original свойство p02 следует из выбранной взаимоисключающей разметки состояний; это полезная sanity-check кодирования, но не самостоятельное доказательство корректности полноценного конкурентного протокола. Мутация overlap_labels показывает, что сама формула способна обнаружить нарушение.

Файл `SPECIFICATIONS.md` объясняет формулы, классификацию и точные CTL-эквиваленты, которые использует независимый Python-checker. `EF error` включено намеренно: его ложность требует обосновать отсутствие подходящего пути, а не показать один неудачный путь.

## Реально вычисленные результаты Python

T/F — истинность свойства из s0, не факт успешного выполнения инструмента.

| Модель | p01 | p02 | p03 | p04 | p05 | p06 |
|---|---|---|---|---|---|---|
| original | T | T | T | F | F | F |
| fixed | T | T | T | T | T | F |
| error_transition | F | T | T | F | F | T |
| overlap_labels | F | F | F | F | F | T |
| bad_ack_successor | T | T | F | T | T | F |

У original безопасность есть, но нет гарантии живости. Кратчайший характерный контрпример response:

```text
prefix: s0 -> s1
cycle:  s1 -> s1 -> ...  (бесконечно)
```

У fixed достижимый граф — цикл s0→s1→s2→s0, поэтому ack возникает регулярно. Ошибка s3 по-прежнему недостижима. Поэтому все пять требований истинны, а диагностический EF error ложен — это желаемый результат.

У error_transition кратчайший путь к ошибке — s0→s1→s3. Это одновременно контрпример safety и положительное свидетельство истинности EF error.

Подробные множества истинности, итерации EF/AF и контрпримеры — в `generated/*.json`, читаемый пересказ — в `generated/*.log` и `REPORT.md`.

## Что именно проверяет Python

`checker.py` содержит точный explicit-state CTL-checker для конечных тотальных графов без fairness: EX/AX/EF/AF/EG/AG/EU/AU и булевы связки. Он вычисляет неподвижные точки, а не только перебирает трассы до произвольной глубины.

Это **не общий LTL-checker**. Четыре используемых LTL-шаблона явно переведены в эквивалентные CTL-формулы для универсальной проверки именно этих шаблонов. Произвольные LTL сюда передавать нельзя. Fairness отвергается явно, а не игнорируется.

Доказательства отсутствия пути и циклы проверяются тестами. Успех тестов Python не заменяет требуемый заданием запуск NuSMV/nuXmv.

## Как используется ваше HW4

HW5 по заданию не является следующим оптимизационным проходом HW4: основная модель берётся из P09. Но интеграция с вашим кодом реализована и реально проверена отдельно:

1. В `vendor/hw4_cfg.py` сохранена **неизменённая функция cfg()** из вашего HW04/ir.py; добавлены только её две внешние зависимости-шима.
2. В `examples/hw4_loop_sum.ir.json` перенесён прочитанный реальный IR `generated/loop_sum/ir_after.json` из вашего репозитория.
3. `hw4_bridge.py` использует этот cfg(), строит модель положения в блоках, экспортирует SMV/DOT и проверяет EF done, AF done и стабильность выхода.
4. При желании можно загрузить весь ваш локальный HW04/ir.py вместо сохранённого фрагмента.

```bash
# Полностью автономная демонстрация на реальном IR из вашего HW4
python3 main.py export-hw4 examples/hw4_loop_sum.ir.json --out generated/hw4_cfg

# Непосредственно ваш установленный HW4 и его результат
python3 main.py export-hw4 ../HW04/generated/loop_sum/ir_after.json --hw4-dir ../HW04 --out generated/hw4_local

# Сравнить локальный cfg() с сохранённой версией
python3 run_tests.py --hw4-dir ../HW04
```

**Ограничение:** это только control-flow overapproximation: условия ветвлений становятся недетерминированными, значения/вызовы/исключения не моделируются. Одна позиция — один базовый блок, а return-блок получает самопетлю. В этой абстракции EF done истинно, AF done ложно: можно всё время выбирать обратное ребро цикла. Это **не контрпример завершимости настоящего loop_sum** — такой путь может быть невозможен при конкретных значениях i/n. Не переносите next-свойства между уровнями «инструкция» и «блок» без отдельного доказательства.

Файлы HW04 не изменяются. Источники и commit указаны в `INTEGRATION.md`.

## Состав и выходы

- `models/*.smv` — пять готовых моделей, по шесть именованных спецификаций в каждой.
- `models/*.json` — те же явные графы с разметкой.
- `protocol.py`, `checker.py`, `smv.py` — модель, точный ограниченный checker, SMV exporter.
- `main.py`, `run_nusmv.py`, `run_tests.py`, `test_mc.py` — запуск и тесты.
- `hw4_bridge.py`, `vendor/`, `examples/` — фактическое переиспользование HW4.
- `generated/*.json`, `*.log`, `*.dot` — реально полученные Python-результаты и доказательства.
- `generated/nusmv/` — реальный статус внешнего запуска; после установки инструмента здесь будут его сырые логи и команды.
- `REPORT.md`, `SPECIFICATIONS.md`, `INTEGRATION.md`, `DEFENSE.md` — отчёт, спецификации, происхождение и план демонстрации.

NuSMV-логи при реальном запуске могут отличаться длиной/порядком трассы от кратчайших свидетельств Python: проверять нужно корректность пути и verdict, а не побайтовое совпадение контрпримеров.
