# Спецификации и семантика HW5

Модель имеет единственное начальное состояние s0, конечное множество состояний и тотальное отношение переходов. Рассматриваются бесконечные пути без fairness. В formulas SMV определены атомы idle/req/ack/error; эти DEFINE-предикаты не ограничивают переходы.

## Шесть основных свойств

### p01_no_error — безопасность

```smv
CTLSPEC NAME p01_no_error := AG (!error);
```

На любом пути в любой момент error ложно. Нарушение имеет конечный плохой префикс, заканчивающийся ошибкой. Проверяется на всём достижимом пространстве; это не ограничение INVAR, удаляющее ошибки из модели.

### p02_no_overlap — безопасность разметки

```smv
LTLSPEC NAME p02_no_overlap := G (!(req & ack));
```

Нельзя находиться одновременно в запросе и подтверждении. Нарушение обнаруживается по одному состоянию. Для универсальной проверки эквивалентно CTL `AG (!(req & ack))`.

В основной one-hot модели это структурная sanity-check; чтобы проверка не была чисто декларативной, мутация overlap_labels делает нарушающее состояние достижимым.

### p03_ack_to_idle — безопасность следующего шага

```smv
LTLSPEC NAME p03_ack_to_idle := G (ack -> X idle);
```

За каждым ack непосредственно следует idle. Плохой префикс содержит ack и следующий не-idle. Универсальный CTL-эквивалент: `AG (!ack | AX idle)`.

Здесь X означает один переход данного автомата. Свойство чувствительно к добавлению промежуточных состояний, поэтому нельзя без оговорок проверять его на другом уровне детализации.

### p04_response — живость

```smv
LTLSPEC NAME p04_response := G (req -> F ack);
```

Каждый запрос когда-нибудь обслуживается, без фиксированного предела ожидания. F включает и текущую позицию. В baseline req и ack взаимоисключающие, так что ответ требует продвижения.

На конечном графе нарушение допускает lasso: конечный путь к необслуженному запросу и бесконечный цикл без ack. Универсальная проверка данного шаблона эквивалентна `AG (!req | AF ack)`. Это не утверждение, что любую LTL-формулу можно перевести в CTL.

### p05_recurring_ack — живость повторения

```smv
LTLSPEC NAME p05_recurring_ack := G F ack;
```

На каждом пути ack возникает бесконечно часто. Для универсальной проверки этого шаблона эквивалентно CTL `AG AF ack`.

В общем случае это не то же самое, что response: если после некоторого момента запросов нет, response может быть истинно вакуозно, а GF ack — ложно. В нашей модели idle принудительно порождает новый req, поэтому оба свойства связаны структурой протокола.

### p06_error_reachable — экзистенциальная достижимость

```smv
CTLSPEC NAME p06_error_reachable := EF error;
```

Есть ли хотя бы один путь, достигающий error? True подтверждается конечным свидетельством. False нельзя обосновать одним неудачным путём: нужны полное множество достижимости или множество истинности EF error. На данном тотальном графе это отрицание p01 в начальном состоянии; пара включена специально, чтобы показать разные виды обоснований.

## Неподвижные точки

Пусть S — все состояния; EX(Z) — состояния с хотя бы одним преемником в Z; AX(Z) — состояния, все преемники которых лежат в Z. Все графы тотальны, поэтому нет скрытой вакуозной истинности AX в deadlock.

```text
EF p = least Z: p ∪ EX(Z)
AF p = least Z: p ∪ AX(Z)
EG p = greatest Z: p ∩ EX(Z)
AG p = greatest Z: p ∩ AX(Z)
E[p U q] = least Z: q ∪ (p ∩ EX(Z))
A[p U q] = least Z: q ∪ (p ∩ AX(Z))
```

Для EF/AF стартуем с p; для EG/AG — со S. Алгоритм завершается после стабилизации конечного множества. В Python поддержана только эта семантика без fairness. NuSMV различает SPEC/CTLSPEC и LTLSPEC; fairness при её наличии ограничивает множество рассматриваемых путей. В наших файлах fairness специально отсутствует. [web:30][web:31]

## Обоснования для экзистенциальных CTL

- True EF error: показать кратчайший путь s0→s1→s3 в error_transition.
- False EF error: показать замкнутое достижимое множество {s0,s1,s2}, не содержащее error, и `Sat(EF error)={s3}`.
- Для произвольных ложных EX/EG/EU также нельзя в общем случае предъявить один «плохой путь» как полное доказательство отсутствия хорошего пути. Здесь из экзистенциальных формул в основном наборе используется EF.

Абсолютной корректности реального протокола результаты не доказывают: они относятся к указанному графу, разметке, началу и отсутствию дополнительных предположений.
